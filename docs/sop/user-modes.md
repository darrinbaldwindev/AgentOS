# SOP-UX-001 — Simple / Essentials / Tech Head Documentation Contract

**Owner:** SOP Overseer  
**Status:** PRODUCT DIRECTION / IMPLEMENTATION-DEPENDENT  
**Version:** 0.1-draft  
**Last verified:** 2026-09-15

## Principle
Simple, Essentials and Tech Head are presentation/disclosure modes over the same canonical AgentOS truth. They are not authority levels, safety levels, commercial plans, or separate runtime states.

## One-truth contract
A mode may change wording density, default visibility, explanation depth and access to diagnostic detail. It must not change the underlying mission status, authority decision, evidence state, Green state, PRS state, cost/budget fact, recovery requirement or stop state.

### Simple
Prioritise clear outcome and next action. Show trust-critical state even when technical detail is collapsed. Never hide required approval, uncertain execution, recovery requirement, failed verification or material external action.

### Essentials
Expose the core operational chain: goal/task, current stage, important permissions/approvals, files/resources affected, cost where material, evidence/verification and blockers.

### Tech Head
Expose deep operational detail where implemented: correlation IDs, worker/provider/capability, exact evidence/receipt references, policy/authority decisions, runtime/head/version, test/verification state, recovery details and assurance scope.

## Truthful state language
All modes preserve distinctions such as:
- `Stop requested` vs `Execution stopped`;
- `Execution finished` vs `Verified`;
- `Verified` vs `PRS assured`;
- `Failed` vs `Contained`;
- `Unknown` vs `Not applicable`;
- `Recovery required` vs `Retry available`.

## Terminology migration
Older `Everyday` wording is historical and must not silently override current Simple / Essentials / Tech Head direction. Internal `Basic` labels may remain implementation details where changing them would create unrelated code churn; public documentation must state the actual current UI wording once implementation evidence is established.

## Persona independence
Willow, Isla, Jack and Henry may be default personas/presentation where applicable. Documentation must not make persona names the permanent architectural identity of canonical roles unless implementation deliberately establishes that invariant.

## Revalidation
Revalidate against frontend state contracts, mode implementation, role/persona architecture, pricing/tier changes and any change to trust-critical states.
